一、高频题（20 题）

1. 性能测试的目的是什么？

【考点】 性能测试价值定位，避免"为了压测而压测"。

【参考答案】 性能测试核心目的有四点：① 验证容量——系统能扛多少并发/吞吐，能否满足业务峰值；② 发现瓶颈——定位响应慢、资源耗尽的根因；③ 保障稳定——长时间运行不退化（内存泄漏/连接泄漏）；④ 支撑决策——容量规划、扩容依据、SLA 达标确认。本质是用数据回答"系统快不快、稳不稳、够不够"。

【结合你的经验】 资金系统里批量支付、对账都是定时高负载任务，性能不达标直接影响客户代发薪资、清算时效，所以性能测试不是"锦上添花"，是资损与履约的红线。

2. 负载 / 压力 / 容量 / 稳定性 / 尖峰测试区别

【考点】 性能测试类型辨析，基础必问。

【参考答案】 - 负载测试：逐步加压到预期峰值，看系统在正常目标下的表现（找拐点前） - 压力测试：继续加压超过峰值直到崩溃，找极限与失效点、验证降级 - 容量测试：确定最大支撑能力（如最大 TPS/用户数），用于容量规划 - 稳定性测试（ endurance）：预期负载下长时间跑（如 8-24h），查内存/连接泄漏 - 尖峰测试（spike）：瞬间剧增负载再回落，验证弹性与恢复（如秒杀）

类型 目标 时长 负载特征
负载 达标验证 中 渐进到峰值
压力 找极限 短 超峰值
容量 最大能力 中 极限附近
稳定性 查泄漏 长 恒定中载
尖峰 弹性 短 骤增骤降

【结合你的经验】 银企直联白天是持续中负载（稳定性关注），月末/代发日是尖峰（spike），我按这两种特征分别设计场景。

【追问链】 尖峰和负载区别？→ 稳定性跑多久？→ 怎么判断到极限了？

3. 核心指标详解：TPS / QPS / RT / 并发数 / 错误率 / 资源利用率

【考点】 性能指标定义与参考标准，必须张口就来。

【参考答案】 - TPS（每秒事务数）：系统每秒处理的事务数，最核心吞吐指标 - QPS（每秒查询数）：每秒查询/请求数，常等同 TPS 在接口语境 - RT（响应时间）：单次请求耗时；关注均值、P90、P95、P99（长尾更关键） - 并发数：同时向系统发起请求的用户/线程数 - 错误率：失败请求占比，一般要求 < 0.1%~1% - 资源利用率：CPU/内存/IO/网络/连接池占用，健康线 CPU<70%、内存有冗余

参考标准（资金系统经验值）：

指标 健康参考
RT（接口） P99 < 500ms，核心 < 200ms
TPS 按业务峰值定，如批量支付 ≥ 设计目标
错误率 < 0.1%
CPU 持续 < 70%
内存 无持续增长（防泄漏）

【结合你的经验】 批量支付接口我重点关注 TPS（决定代发时效）和 P99 RT（避免单笔卡死整批），错误率必须近 0，因为资损不可接受。

【追问链】 P99 为什么比均值重要？→ TPS 上不去先怀疑什么？→ 错误率突增怎么看？

4. TPS 和响应时间、并发数的关系曲线（拐点怎么理解）

【考点】 性能模型理解，考察是否真懂曲线。

【参考答案】 经典关系： - 低并发时，并发↑ → TPS 线性↑、RT 基本平稳（资源充足） - 到某点后，并发继续↑ → TPS 增速放缓、RT 开始明显上升（资源争用） - 拐点（ knee point）：TPS 不再明显增长、RT 陡升的位置——这是系统"舒适区"上限，是容量规划基准 - 再加压 → TPS 下降、RT 暴涨甚至错误率上升（过载崩溃）

文字图：

TPS
 ↑        ___________
 |       /           \  (过载区，TPS↓)
 |      /   拐点→
 |     /   (RT↑陡)
 |    /  (线性区)
 +---/----------------→ 并发数
      RT 在拐点后飙升

【结合你的经验】 我设计批量支付压测时，就是找这个拐点——目标不是压崩，而是确认"业务峰值并发"位于拐点左侧且留 30% 余量。

【追问链】 拐点怎么测得准？→ RT 和 TPS 谁优先？→ 没到拐点但错误率升了说明啥？

5. 吞吐量拐点出现后系统发生了什么？

【考点】 拐点背后的资源机理。

【参考答案】 拐点之后 TPS 不涨反降、RT 飙升，本质是资源饱和 + 争用加剧： - CPU 跑满，上下文切换暴增，有效计算占比下降 - 线程池/连接池耗尽，请求排队（队列积压 → RT 上升） - 内存压力大，GC 频繁（STW 卡顿）甚至 OOM - 数据库锁等待、慢 SQL 放大，成为瓶颈传导 - 网络带宽或文件 IO 打满 此时系统进入"越压越慢"的恶性循环，再加压只会雪崩。

【结合你的经验】 资金系统常见拐点是 DB 连接池耗尽——批量支付一多，连接被长事务占满，后续请求排队，RT 从 100ms 飙到秒级。所以压测我必盯连接池。

【追问链】 怎么确认是连接池不是 CPU？→ 队列积压怎么观测？→ 拐点能靠调参推后吗？

6. 性能测试完整流程

【考点】 工程化闭环，是否走过完整性能项目。

【参考答案】 八步： 1. 需求分析：明确目标（TPS/RT/并发）、场景、SLA 2. 场景设计：基准/负载/压力/稳定性场景及数值 3. 脚本开发：JMeter 录/写脚本，参数化、关联、断言 4. 环境准备：独立压测环境、数据铺量、监控埋点 5. 执行压测：按场景逐步加压，记录指标 6. 监控采集：APM/系统/DB/中间件全链路监控 7. 分析调优：定位瓶颈、提优化、复测验证 8. 报告输出：结论、瓶颈、建议、风险

【结合你的经验】 我做渠道接口和批量支付压测就是这条链路：先定代发时效目标（SLA），再设计负载+尖峰场景，用 JMeter 压，Fiddler 辅助定位，Linux 看资源，最后出报告给研发调优。

7. 性能测试场景怎么设计？（配数值例子）

【考点】 场景设计落地能力。

【参考答案】 四类场景配数值（以批量支付为例，目标峰值 200 TPS）： - 基准场景：1-10 并发，单用户跑通，得 RT 基线（如 80ms） - 负载场景：从 50 渐进加到 250 并发，每档稳 5 分钟，画 TPS-RT 曲线，找拐点 - 压力场景：加到 400+ 并发直到错误率 >1% 或 TPS 下降，记录极限（如 320 TPS） - 稳定性场景：180 并发（≈90% 峰值）跑 8 小时，查内存/连接是否泄漏

8. JMeter 架构与核心组件

【考点】 JMeter 组成原理。

【参考答案】 JMeter 是多线程模拟请求的 Java 工具，核心组件： - Test Plan：根容器 - 线程组（Thread Group）：并发用户数、 ramp-up、循环次数——压测的"发动机" - 取样器（Sampler）：HTTP/FTP/JDBC 请求，发起真实调用 - 配置元件（Config）：HTTP 请求默认值、CSV 数据集、Header 管理 - 前置/后置处理器：发前造数据、收后提取（正则/JSON 提取器） - 断言（Assertion）：校验响应，过滤错误 - 定时器（Timer）：思考时间、集合点（同步并发） - 监听器（Listener）：结果树、聚合报告、图表 - 逻辑控制器：If/循环/事务，组织复杂场景

【结合你的经验】 批量支付压测我用线程组控并发、HTTP 取样器发请求、CSV 参数化账号、JSON 提取器取 token、聚合报告看 TPS/RT——是标准 JMeter 组合。

【追问链】 线程数和并发数等价吗？→ 集合点干嘛用？→ 监听器太多为什么影响性能？

9. JMeter 压测一个接口的完整操作步骤

【考点】 实操熟练度。

【参考答案】 步骤： 1. 新建 Test Plan → 加 线程组（设并发、ramp-up、循环） 2. 加 HTTP 请求默认值（base_url）+ HTTP Header 管理器（Content-Type/token） 3. 加 HTTP 请求（Sampler）：填路径、方法、Body 4. （需登录）加 登录请求 + JSON 提取器 取 token，用 后置处理器 写入变量 5. 加 CSV Data Set Config 参数化（账号/金额） 6. 加 断言（响应码/业务码）过滤失败 7. 加 聚合报告 / 查看结果树 监听器 8. 调 ramp-up 渐进加压，命令行 jmeter -n -t xx.jmx -l result.jtl 跑，出 HTML 报告

【结合你的经验】 我压渠道查询接口就用这套：Header 带 token、CSV 铺多账号、聚合报告盯 TPS 和 P99，命令行跑避免 GUI 耗资源。

10. JMeter 参数化 4 种方式

【考点】 数据驱动压测能力。

【参考答案】 四种： 1. CSV Data Set Config：最常用，外部 CSV 读账号/金额等，支持多列、循环 2. 用户参数（User Parameters）：线程组级变量，适合少量定值 3. 函数助手（__Random/__time/__UUID）：动态生成随机数、时间戳、唯一流水号 4. 前置/BeanShell/Groovy：脚本生成复杂数据（如签名、加密报文）

方式 适用
CSV 大批量真实数据
用户参数 少量定值
函数 随机/时间戳/UUID
脚本 加密/签名/复杂逻辑

【结合你的经验】 批量支付压测我用 CSV 铺多账户多金额，用 __time/__UUID 生成唯一批次号和流水号，避免重复提交和幂等拦截干扰压测数据。

11. JMeter 怎么提取和传递 token？

【考点】 关联（correlation）实操，压测登录态接口必会。

【参考答案】 两步： 1. 提取：在登录请求后加 后置处理器 - JSON 提取器：$.data.token → 存变量 token - 正则提取器："token":"(.+?)" → 变量（非 JSON 时用） 2. 传递：后续请求 Header 管理器写 Authorization: Bearer ${token}，或用变量引用

登录 HTTP 请求
  └─ JSON 提取器: names=token, expr=$.data.token
业务 HTTP 请求
  └─ HTTP Header: Authorization = Bearer ${token}

【结合你的经验】 渠道接口都要鉴权，我每个压测脚本都先登录提取 token 再并发跑业务，否则全 401，压测无意义。

【追问链】 多个 token 怎么处理？→ token 过期压测中途失效怎么办？→ 分布式下变量共享吗？

12. JMeter 分布式压测怎么做？

【考点】 大并发压测扩展能力。

【参考答案】 单机线程有限（CPU/端口瓶颈），需多机分担： 1. 选 1 台 Master（控制）+ N 台 Slave（Agent） 2. 所有机装同版本 JMeter，Slave 开 jmeter-server 3. Master 的 jmeter.properties 配 remote_hosts=ip1:1099,ip2:1099 4. 执行 jmeter -n -r -t xx.jmx -l result.jtl（-r 调远程） 5. 结果汇总回 Master 注意：参数化 CSV 各 Slave 都要有；保证网络互通；Slave 数量按总并发/单机能力估。

【结合你的经验】 我了解分布式架构和配置，批量支付要上千并发时单机压不动，会用 Slave 分担；我实操以单机+合理线程为主，分布式有方法论和配置基础。

13. 怎么定位性能瓶颈？（完整排查链路）

【考点】 瓶颈定位体系，性能面试核心。

【参考答案】 自顶向下全链路排查：

压测端 → 网络 → 应用 → 中间件 → 数据库
  • 压测端：是否自身瓶颈（CPU 满/端口耗尽）→ 加 Slave 或降监听开销
  • 网络：带宽/延迟/丢包 → ping/iperf/tcpdump
  • 应用：CPU/内存/线程/GC → top/jstack/jstat、APM（SkyWalking）
  • 中间件：Nginx/Tomcat 线程池、MQ 堆积、Redis 命中率/慢命令
  • 数据库：连接池、慢 SQL、锁等待、索引 → slow log/explain/show processlist

每环用对应工具，定位到"哪一层先到瓶颈"，再深挖该层。

【结合你的经验】 我定位批量支付慢，先排除压测端（命令行跑），再看应用 CPU 正常但 DB 连接池占满 → 是数据库慢 SQL + 连接未释放，典型的"中间件→DB"链路问题。

【追问链】 怎么确认是应用不是 DB？→ APM 怎么看调用链？→ 没有 APM 怎么查？

14. 数据库慢导致的性能问题怎么排查和优化？

【考点】 DB 性能，资金系统高频瓶颈。

【参考答案】 排查： 1. 开 慢查询日志 slow_query_log，定位慢 SQL 2. EXPLAIN 看执行计划：是否全表扫描、是否用索引、rows 预估 3. SHOW PROCESSLIST 看是否有锁等待、长事务、连接堆积 4. 看连接池配置（maxActive）是否被占满

优化： - 加/调 索引（联合索引最左匹配），避免索引失效（函数/隐式转换） - 改写 SQL：减少 SELECT *、避免 IN 超大、分页优化 - 减少长事务，及时 commit 释放连接 - 读写分离、分库分表（海量流水） - 缓存热点（Redis）降 DB 压力

【结合你的经验】 对账/明细查询慢常因缺索引或分页深；我压测时用 explain 帮研发定位过全表扫描的流水查询，加联合索引后 RT 从秒级降到百毫秒。

二、必背清单

【核心指标一句话】 - TPS=每秒事务数（吞吐核心）；RT 看 P99 不看均值；并发数≠线程数；错误率资金系统近 0；CPU 健康 < 70%

【拐点记忆】 - 拐点前：并发↑ TPS↑ RT 稳；拐点后：TPS 滞涨 RT 飙升；拐点=容量基准，目标负载留 30% 余量

【JMeter 实操口诀】 - 线程组控并发 → Header 带 token → CSV 铺数据 → JSON 提取器取 token → 断言过滤 → 命令行跑 → 聚合报告看 TPS/P99 - 参数化 4 种：CSV / 用户参数 / 函数(__Random __time __UUID) / 脚本 - 分布式：Master+Slave，remote_hosts 配 IP，-r 调远程

【瓶颈定位链路（必背）】 - 压测端 → 网络 → 应用(CPU/GC/线程) → 中间件(连接池/MQ/Redis) → 数据库(慢SQL/锁/连接池) - 每环工具：top/jstack/jstat、iperf/tcpdump、slow log/explain/processlist、SkyWalking

【资金系统性能重点】 - 批量支付：盯 TPS（时效）+ P99 RT（长尾）+ 错误率(≈0) + DB 连接池拐点 - 场景：日常负载 + 月末尖峰(spike) - 常见坑：长事务占满连接池、慢 SQL 全表扫、锁等待

【诚实话术】 - "JMeter 压测设计与执行我实战过（渠道接口+批量支付）；分布式压测和全链路 APM 调优我有方法论和配置基础，复杂场景深度在补齐中，但瓶颈定位链路我完全清楚。"

三、实战演练：给「批量支付接口」设计压测方案

面试被要求"现场设计压测方案"时，按下面结构讲，约 3 分钟，体现测试开发专业度。

1. 明确目标（SLA）

  • 业务背景：资金系统代发薪资/批量代付，月末多客户并发
  • 性能目标（示例）：峰值 200 TPS，P99 RT < 500ms，错误率 < 0.1%
  • 容量余量：按峰值 130% 设计，即按 260 TPS 验证不退化

2. 环境准备

  • 独立压测环境（Docker 起，配置等同准生产：JVM/连接池/DB 参数一致）
  • 铺足量流水数据（百万级，避免小表失真）
  • 监控全开：Prometheus+Grafana（资源）、SkyWalking（链路）、slow log（DB）

3. 脚本设计（JMeter）

  • 线程组：并发梯度 50→100→200→300→400，ramp-up 逐步加压，每档稳 5 分钟
  • HTTP 取样器：批量支付接口，Body 含批次号+多明细
  • 关联：登录提取 token → Header 携带
  • 参数化：CSV 铺付款账号/金额；__UUID 生成唯一批次号（防幂等拦截）
  • 断言：响应码 200 + 业务码成功 + 回执字段存在
  • 定时器：加思考时间模拟真实节奏

4. 场景设计

场景 并发 目标
基准 10 得 RT 基线
负载 50→260 画 TPS-RT 曲线，找拐点
压力 300→400+ 找极限、验证降级
尖峰 骤增到 300 再回落 验证弹性恢复
稳定性 200（≈峰值）跑 8h 查连接/内存泄漏

5. 执行与监控

  • 命令行 jmeter -n -t batch_pay.jmx -l r.jtl -e -o report/ 出 HTML 报告
  • 实时监控：TPS/RT(P90/P99)/错误率 + DB 连接池/CPU/慢 SQL

6. 预期瓶颈与应对（提前预判）

  • DB 连接池满：长事务占连接 → 缩事务 + 调大池 + 连接及时释放
  • 慢 SQL：流水表全表扫 → 加联合索引、分页优化
  • 锁等待：批次号/账户锁 → 降锁粒度、异步化

7. 交付物

  • 压测报告：目标达成情况、拐点位置、资源曲线、Top1 调优项
  • 结论：是否达代发时效 SLA、能否支撑月末尖峰、上线建议与风险

讲法要点：先定 SLA → 再环境/脚本 → 五场景覆盖 → 监控兜底 → 预判瓶颈 → 出报告。这套结构展示"不仅会用工具，更懂性能工程"，是测试开发岗的高分答法。
