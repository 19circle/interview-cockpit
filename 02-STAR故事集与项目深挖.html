02 · STAR故事集与项目深挖

配套文件：《社招自我介绍与求职策略-尹胜.md》（三版自我介绍稿） 本文件是自我介绍稿的"弹药库"——自我介绍只讲结论，这里讲过程、讲细节、讲被追问时怎么接。 用法：先读"使用说明"，再按"口述练习清单"逐个练熟。

怎么练（三遍法，每个故事都要过）

  1. 第一遍·照读：看着逐字稿完整念一遍，找语感，标记拗口的地方。
  2. 第二遍·关键词提示：只看着"关键词卡"复述，卡壳了再回看，直到能顺下来。
  3. 第三遍·脱稿录音：手机录音，全程不看稿，回听找口头禅（"然后""那个""就是"）、找停顿和逻辑断点，再纠一遍。

关键原则：讲结果先讲数字，讲过程先讲动作，讲难点先讲你做了什么决策。面试官记不住细节，但能记住"2人天降到0.5人天"这个数字。

一、四大项目STAR逐字稿（每个项目含：30秒电梯版 + 2分钟完整版）

项目1：报文比对自动化（王牌，主打"推动落地"）

【Situation 背景】 我们做资金管理和银企直联两条产品线，对接40多家银行和金融机构。每次发版，光是渠道报文回归，人工比对就是噩梦。

【30秒电梯版·完整台词】 "我主导做了一个报文比对自动化工具。之前每轮版本回归，我们对40多个银行渠道的报文，全靠人工逐条比对，单轮渠道回归要两个人干两天。我用了日志回放的思路——把交易日志直接回放到比对平台，配置忽略节点，再调优比对规则，把噪音过滤掉。上线后单轮渠道回归从2人天压到了0.5人天，效率翻了四倍。这个工具后来成了我们组发版前的必跑环节。"

【2分钟完整版·完整台词】 "我先说背景。我们在保融做的是资金管理和银企直联，简单说就是帮企业做资金归集、对账，跟40多家银行做系统直连。每次产品发版，最头疼的就是报文回归——银行和我们的交互报文是XML格式的，字段特别多，状态、流水号、金额、时间戳这些，全靠人工拿测试环境和生产环境的报文一条条比对。

当时的情况是，一个渠道一轮回归，两个人要两天。为什么这么慢？第一，报文长，一个报文上百个节点；第二，里面有很多每次都变的字段，比如时间戳、流水号、会话ID，这些你不忽略就会一直报差异；第三，全靠眼睛看，漏看是常态。

我当时的任务，就是把这件事自动化。我的思路不是重新造轮子，而是用日志回放——我们系统本来就会落交易日志，我把这些日志抓出来，按渠道和交易类型回放到我自己搭的比对平台里，平台一边是基准报文，一边是对比报文，自动做节点级比对。

真正的难点在调优。一开始直接跑，差异报告几千条，全是噪音。我做了三件事：第一，配置忽略节点，把时间戳、流水号、会话ID这些动态字段排除；第二，做规则分层，核心金额、状态、账号这些强制比对，描述性字段降级提示；第三，针对每个渠道的报文特性，单独调权重和匹配逻辑。

结果是，单轮渠道回归从2人天降到0.5人天。而且因为比得细，反而比人工更准，之前漏看的字段现在都能抓出来。这个工具不是我一个人闷头写完就完了——我推动它在组里落地，写了使用文档，做了培训，现在是发版前必跑的环节。我认为这比写代码本身更重要，因为工具的价值在于被用起来。"

项目2：DSP自动部署模块（主打"工程化提效"）

【Situation 背景】 测试环境频繁重建，每个渠道单独部署，人工操作又慢又容易出错。

【30秒电梯版·完整台词】 "我做了一个自动部署模块，解决的是测试环境部署慢的问题。原来单渠道部署，从拿包、传包、改配置到起来，人工要三分钟左右，而且渠道多、版本杂，经常配错。我把部署流程做成了脚本化的一键部署，标准化了部署包和配置模板，单渠道部署从3分钟压到10秒以内，而且不再依赖人的细心程度，出错率基本归零。"

【2分钟完整版·完整台词】 "这个项目的背景是我们测试环境要频繁重建。我们对接40多个银行渠道，每个渠道的部署包、配置文件、数据库初始化都不一样。原来一个新渠道或者一次环境重建，测试同学要手动去拿部署包、传上去、改一堆配置项、再启动服务，熟练的人也要三分钟，新人更慢，而且配置项一多，改错一个端口或者账号就起不来，又得从头排查。

我看到这个问题，就决定把它工程化。我做的自动部署模块核心思路是标准化加脚本化：第一，把每个渠道的部署包按统一目录结构规范好；第二，把差异化配置抽成模板，用变量注入，不再手写；第三，用脚本串起拿包、传包、解压、注入配置、启动这一整条链路，做成一键执行。

技术上我用的是Shell加Python做编排，配合我们内部的制品库。部署时只需要选渠道和版本，剩下的全自动。

效果上，单渠道部署从3分钟降到10秒以内，提速将近20倍。更重要的是稳定性——之前人工部署出错要回头查，现在脚本跑失败了也会有明确的错误码和日志，一眼能定位。这个模块后来成了我们环境搭建的标准动作，新人不用再花一周去学怎么部署，十分钟就能上手。"

项目3：环境信息模块全栈开发（主打"独立交付"）

【Situation 背景】 测试环境信息散落各处，谁在用哪套环境、装了什么版本，全靠口头和Excel，混乱且易冲突。

【30秒电梯版·完整台词】 "我独立从零做了一个环境信息管理模块。原来大家抢环境、不知道谁占了哪套、版本对不对，全靠在群里喊。我用FastAPI加Vue3全栈做了一套系统，带JWT登录、RBAC权限、Excel批量导入，把7条产品线的测试环境、版本、负责人都管起来了。上线一年多了，7条产品线、20多个人每天在用。这是我从需求、设计、前后端到上线维护一个人扛下来的。"

【2分钟完整版·完整台词】 "这个项目是我独立交付的，我觉得它最能代表我的全栈能力。背景是，我们公司测试环境特别多，7条产品线、几十套环境，谁在用、装了什么版本、连的哪个库，全靠在群里喊或者记在Excel里，经常撞车，两个人同时用一套环境把数据搞乱。

我主动提出要做一个统一管理平台。技术栈我选了FastAPI做后端，SQLAlchemy加MySQL做持久化，前端Vue3加Element Plus，权限用JWT加RBAC，还做了Excel批量导入，因为大家懒得一条条录。

我讲几个我比较得意的点。第一，权限模型：RBAC，角色分管理员、产品线负责人、普通成员，权限粒度到环境级别，你不是这条线的你连看都看不到。第二，JWT那套，登录签发token，用中间件校验，过期了走刷新token，前端再做路由守卫，没权限的菜单直接不渲染。第三，Excel导入我做了字段校验和去重，导入前先预览，避免脏数据进库。

这个过程我是一人全流程：需求是我跟各产品线聊出来的，设计自己画，前后端自己写，上线自己部署到Docker，后面维护也是我。上线一年多了，7条产品线、20多个人每天在用，没出过大问题。这个项目的意义不只是做了个工具，而是证明我能在没有别人兜底的情况下，把一个系统从0到1稳稳交出去。"

项目4：7.0→8.0升级回归 + 生产事故拦截（主打"风险把控"）

【Situation 背景】 大版本升级，回归范围大，上线前发现重大隐患。

【30秒电梯版·完整台词】 "在7.0升8.0那次大版本，我负责整体回归，维护着1900多条回归用例。最关键的是上线前，我通过白盒定位，发现了一个银行交互关键节点名称的配置错误——如果带着这个错误上线，客户会批量支付失败。我定位到是配置层面把节点名写错了，及时拦了下来，避免了一次生产事故。这件事后来给了我公司那个季度的极致奖。"

【2分钟完整版·完整台词】 "这个项目讲的是风险把控。7.0升8.0是个大版本，涉及两条产品线、几十个渠道，回归面非常大。我手里维护着1900多条回归用例，这次升级我带着把这1900多条全过了一遍，该补的补，该调优先级的调，确保覆盖到新功能的改造点。

真正的高光时刻是上线前。我们在做渠道连通性验证的时候，我发现某家银行的交互一直不对，但表象很隐蔽——不是直接报错，而是返回的状态码看起来正常，但下游对不上。我没有只停在测试层面，而是做白盒定位：从Controller层看请求入口，到Service看业务逻辑，再到Mapper层看SQL，最后发现是银行交互的一个关键节点名称，在配置文件里写错了——把对方系统返回的节点名和我们解析的节点名对不上，导致支付指令的某段关键报文没被正确解析。

如果带着这个错误上线，客户那边的批量支付会大面积失败，这是直接的生产事故。我在上线评审前把这个风险点提出来，拉着开发和配置负责人确认，确实是个配置错误，改完重测通过，拦在了上线前。

这件事给了我公司那个季度的极致奖。我觉得做测试，尤其是金融科技这种容错率极低的领域，价值不只是发现bug，更是你要能判断这个bug上线后意味着什么——批量支付失败，那是真金白银的损失。这种风险嗅觉，我觉得是我的核心优势。"

二、量化口径推算（被质疑数字时的标准答案）

面试官怀疑你"数字是不是吹的"，不要慌，给他看你的推算逻辑。数字要能还原到动作上。

"2人天 → 0.5人天" 怎么算的

"这个数字是这么来的。原来人工比对，一个渠道一轮，一个测试同学要花约4小时纯比对时间——因为报文长、节点多、还要交叉核对好几笔交易。一个人一天有效比对时间算8小时，那一个渠道就要0.5人天；我们有40多个渠道，如果全量回归一轮，就是40乘以0.5，等于20人天，但发版前我们一般抽核心的4个渠道做全量、其余抽样，实际一轮投入约2人天（两个人干一天）。

自动化之后，脚本跑一遍几分钟，人只需要做异常复核和规则调优，一个渠道从0.5人天降到约0.06人天，一轮核心回归两个人合计0.5人天就能收工。所以'2人天→0.5人天'指的是发版前标准回归轮次的实际人力投入，不是单渠道极限值，口径是'一轮标准回归的人力'。"

"3分钟 → 10秒" 怎么算的

"单渠道部署，原来人工步骤是：登录制品库下载包（约30秒）、传包解压（约40秒）、改6-8个配置项（约60秒）、启动并验证（约50秒），熟练工连贯操作约3分钟，新人更慢且易错。自动化后，选渠道和版本点执行，脚本串起全部步骤，实测平均9到10秒完成，包含启动后健康检查。所以'3分钟→10秒'是单渠道一次完整部署的耗时，从人操作到脚本执行。"

"1900+ 用例" 口径

"这1900多条是我接手回归体系后，两年多时间里逐步积累和维护的。覆盖资金管理和银企直联两条产品线的功能用例、接口用例、渠道连通性用例，其中接口和渠道类占大头。我会按版本标记用例归属和优先级，升级时筛核心用例跑，所以这个数字是我实际维护的活用例总数，不是历史归档的死用例。"

"40+ 客户 / 40+ 渠道" 口径

"40多家金融机构客户，是指我们产品服务的银行、财务公司、企业司库这类客户；40多个银行渠道，是指我们系统直连的银行通道，比如各家银行的银企直联接口。客户和渠道不是一个概念——一个客户可能走多个渠道，一个渠道也服务多个客户。这两个数字是我所在团队实际对接的规模，我在客户现场支持半年，对这些渠道的报文差异是亲手摸过的。"

三、三大高难追问完整答案

白盒定位完整案例逐字稿（现象 → 排查 → 定位到Mapper层SQL逻辑 → 根因 → 验证）

"我讲一个白盒定位的真实案例。现象是：某银行渠道一笔代发交易，状态显示成功，但客户对账时发现这笔钱没出去，钱卡在中间状态。

我排查的思路是自顶向下。先看Controller层，请求进来了，参数没问题；再看Service层业务逻辑，代发是异步的，状态流转靠一个回调更新，看起来也正常；然后我钻到Mapper层看SQL——这一步是关键，我发现更新交易状态的SQL，条件是按'渠道流水号+状态'去匹配，但这个银行的渠道流水号在回写时带了前缀，而我们SQL里没做trim，导致update affect_rows = 0，状态永远更新不上去。

根因就是：Mapper层这条SQL的匹配条件没有对齐银行返回的流水号格式，少了一层清洗。

验证我做了两步：第一，我在测试环境构造同样带前缀的流水号，复现了卡状态；第二，我提的修复方案是SQL里加trim或者在Service层统一清洗流水号，改完重跑，affected_rows正常，状态流转通了。这个案例让我养成一个习惯：测试不能只看输入输出，要看代码怎么处理的中间态，尤其是金融场景，状态机错一格就是钱的问题。"

FastAPI选型对比逐字稿（vs Django / Flask）

"选FastAPI，我是认真比过的。对比Django：Django太重，自带ORM、admin、模板，我们要的是轻量API服务，Django的包袱反而碍事，而且Django异步支持起步晚，我们这套环境模块不需要它那套全家桶。对比Flask：Flask够轻，但它是同步的，缺少原生异步，而且没有内置的数据校验和自动文档——这两点对我们很重要。

FastAPI打动我的点：第一，基于Pydantic，请求参数和响应结构直接声明式校验，前端传错字段后端直接拦，不用我手写一堆if判断；第二，异步原生支持，环境信息查询要并发拉多个数据源，async/await很顺手；第三，自动生成OpenAPI文档和Swagger UI，前后端联调不用再写接口文档，省了我大量沟通成本；第四，轻量，启动快，跟Vue3前端配合清爽。所以综合下来，FastAPI是这套内部工具的最优解，不是追新。"

JWT + RBAC实现逐字稿（token签发 / 校验中间件 / 过期刷新 / 角色表设计 / 前端路由守卫）

"权限这块我是这么落地的。登录时，后端用JWT签发一个token，payload里放用户ID和角色，用密钥签名，设一个短时效（比如2小时）。前端拿到token存起来，之后每个请求在Header里带Authorization。

服务端我用了一个校验中间件：每次请求进来，中间件先解析token，验签名、验过期，通过才放行，并把用户信息注入请求上下文。过期处理我用的是双token——access token短效，refresh token长效，access过期了前端拿refresh去换新的，用户无感。

RBAC的表设计是三张：用户表、角色表、权限表，再加两张关联表（用户-角色、角色-权限），权限粒度到环境级别。中间件里除了验登录，还会按当前请求的资源和角色去查权限表，没权限直接403。

前端我也做了路由守卫：Vue Router的beforeEach里校验有没有token、角色能不能进这个路由，没权限的菜单直接不渲染，做到前后端双重拦截。这样即使有人绕过前端直接调接口，后端中间件也兜得住。"
