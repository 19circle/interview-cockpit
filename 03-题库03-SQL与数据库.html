一、高频题（30题）

1. 内连接/左连接/右连接/全连接区别

【考点】多表关联语义与结果集差异。 【参考答案】 - INNER JOIN（内连接）：只返回两表都满足连接条件的记录，即交集。 - LEFT JOIN（左连接）：返回左表全部记录 + 右表匹配记录，右表无匹配则补 NULL。 - RIGHT JOIN（右连接）：与左连接相反，返回右表全部。 - FULL JOIN（全连接）：左右表并集，MySQL 不直接支持，需用 LEFT JOIN + UNION + RIGHT JOIN 模拟。

-- 内连接：只取有订单的用户
SELECT u.name, o.order_id
FROM user u INNER JOIN orders o ON u.id = o.user_id;

-- 左连接：所有用户 + 其订单（无订单也显示）
SELECT u.name, o.order_id
FROM user u LEFT JOIN orders o ON u.id = o.user_id;

-- 右连接
SELECT u.name, o.order_id
FROM user u RIGHT JOIN orders o ON u.id = o.user_id;

图解（A∩B 交集 / A 全量 / B 全量 / A∪B 并集）。

【结合你的经验】银企直联里"渠道配置表"和"交易流水表"常用左连接：查某渠道下所有交易及其对账状态，即使某笔交易还没回盘也能查出来，避免漏掉挂账。 【追问链】左连接后 WHERE 过滤右表 NULL 会变成内连接效果，为什么？→ 全连接 MySQL 怎么实现？ [ ] 已掌握

2. WHERE vs HAVING

【考点】过滤时机不同。 【参考答案】WHERE 在分组前过滤行，作用于单条记录，不能用聚合函数；HAVING 在 GROUP BY 之后过滤分组结果，可用聚合函数。执行顺序：WHERE → GROUP BY → HAVING → SELECT。

-- 错：WHERE 里不能用聚合
SELECT channel_id, COUNT(*) FROM trans WHERE COUNT(*)>10 GROUP BY channel_id;
-- 对：HAVING 过滤分组
SELECT channel_id, COUNT(*) AS cnt
FROM trans GROUP BY channel_id HAVING COUNT(*)>10;

【结合你的经验】统计每个银行渠道当日交易笔数时，先 WHERE 过滤交易日，再 HAVING 筛出笔数>1000 的渠道做重点关注。 【追问链】WHERE 能不能写在 HAVING 前面性能更好？→ 聚合后还能不能再 WHERE？ [ ] 已掌握

3. GROUP BY 使用规则与常见坑

【考点】非聚合列必须出现在 GROUP BY 中（SQL 模式严格）。 【参考答案】SELECT 中出现的列，要么在 GROUP BY 里，要么被聚合函数包裹，否则报错（ONLY_FULL_GROUP_BY 模式下）。常见坑：① 想查"每个渠道最大金额那笔交易的时间"，直接 SELECT time 会随机取；② MySQL 5.7+ 默认开启 ONLY_FULL_GROUP_BY，老代码迁移易报错；③ GROUP BY 含 NULL 会把 NULL 当一组。

-- 坑：time 不在 GROUP BY 也未聚合，严格模式报错
SELECT channel_id, time, MAX(amount) FROM trans GROUP BY channel_id;
-- 正确：用窗口函数取每渠道最大金额记录
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER(PARTITION BY channel_id ORDER BY amount DESC) rn
  FROM trans
) t WHERE rn=1;

【结合你的经验】资金交易按渠道分组统计时，曾因 SELECT 多写了未聚合的"记账状态"列在生产环境出错，后来统一用窗口函数改写。 【追问链】ONLY_FULL_GROUP_BY 能关吗？关了有什么风险？ [ ] 已掌握

4. 子查询 vs 连接哪种好

【考点】执行计划与可读性权衡。 【参考答案】没有绝对优劣。关联子查询（如 WHERE id IN (SELECT...)）早期 MySQL 优化差、易逐行执行；JOIN 通常更易被优化器改写成 hash/merge join。但 EXISTS 在"存在即返回"场景比 IN 更优（尤其子查询结果集大时短路）。经验：小表 IN 没问题；大表优先 JOIN 或 EXISTS；需去重时用 DISTINCT 或 GROUP BY 配合。

-- IN 子查询
SELECT * FROM trans WHERE channel_id IN (SELECT id FROM channel WHERE type='BANK');
-- 改写成 JOIN（更利于优化）
SELECT t.* FROM trans t JOIN channel c ON t.channel_id=c.id WHERE c.type='BANK';

【结合你的经验】1900+ 回归用例里，我习惯把"查某渠道交易"的子查询改成 JOIN，批量跑回归时单轮时间从 2 人天压到 0.5 人天，部分得益于 SQL 改写。 【追问链】IN 和 EXISTS 在 NULL 上的区别？→ NOT IN 含 NULL 为什么全空？ [ ] 已掌握

5. 窗口函数：row_number/rank/dense_rank

【考点】分组排名三大函数差异 + TopN 取数。 【参考答案】 - ROW_NUMBER：连续不重复序号（1,2,3,4），并列也各占一位。 - RANK：并列同号，跳过后续号（1,1,3,4）。 - DENSE_RANK：并列同号，不跳号（1,1,2,3）。

SELECT name, score,
  ROW_NUMBER() OVER(ORDER BY score DESC) rn,
  RANK()       OVER(ORDER BY score DESC) rk,
  DENSE_RANK() OVER(ORDER BY score DESC) drk
FROM stu;
-- 分组取每渠道 Top3 交易
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER(PARTITION BY channel_id ORDER BY amount DESC) rn
  FROM trans
) t WHERE rn<=3;

【结合你的经验】对账时按"渠道+交易日"分组取金额最大的几笔做抽样复核，用 ROW_NUMBER 一行搞定，替代原来写存储过程循环。 【追问链】取每组最后一条用什么？→ 窗口函数能加 WHERE 在 OVER 里吗？ [ ] 已掌握

6. 窗口函数：lag/lead

【考点】前后行取值，做环比/差值。 【参考答案】LAG(col,n,default) 取前 n 行值，LEAD(col,n,default) 取后 n 行值，常与 PARTITION BY + ORDER BY 配合做相邻记录对比。

-- 每笔交易与上笔交易金额差值
SELECT channel_id, trans_time, amount,
  LAG(amount) OVER(PARTITION BY channel_id ORDER BY trans_time) prev_amt,
  amount - LAG(amount) OVER(PARTITION BY channel_id ORDER BY trans_time) diff
FROM trans;

【结合你的经验】资金系统里用 LAG 比对同一账户相邻两笔余额，发现"银行回盘金额与前一笔差了整数倍"的异常，定位到报文解析错位。 【追问链】LEAD 默认值怎么设？→ 跨组边界会取到别的组吗？ [ ] 已掌握

7. 窗口函数：sum over 累计求和

【考点】累计/滑动聚合。 【参考答案】SUM(amount) OVER(PARTITION BY channel_id ORDER BY trans_time) 实现组内按序累计；加 ROWS BETWEEN 2 PRECEDING AND CURRENT ROW 做近 3 行滑动窗口。

SELECT channel_id, trans_time, amount,
  SUM(amount) OVER(PARTITION BY channel_id ORDER BY trans_time) running_total,
  SUM(amount) OVER(PARTITION BY channel_id ORDER BY trans_time
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) last3_total
FROM trans;

【结合你的经验】做渠道当日资金累计流入监控，用累计求和实时看是否逼近额度上限，提前预警。 【追问链】ORDER BY 缺省窗口范围是什么？→ 滑动窗口和累计窗口性能差别？ [ ] 已掌握

8. UNION vs UNION ALL

【考点】去重代价。 【参考答案】UNION 自动去重（等价于结果再 DISTINCT），UNION ALL 直接拼接不去重。UNION 因去重需排序/哈希，性能更差。确定无重复或不需要去重时一律用 UNION ALL。

SELECT id FROM a UNION SELECT id FROM b;      -- 去重
SELECT id FROM a UNION ALL SELECT id FROM b;  -- 不去重，更快

【结合你的经验】银企直联把多个银行的"成功交易"和"失败交易"两表合并统计时，用 UNION ALL 避免误去重导致笔数少算。 【追问链】UNION 两边列数/类型不一致会怎样？→ 排序怎么加？ [ ] 已掌握

9. 索引是什么？为什么快？

【考点】B+ 树原理通俗讲。 【参考答案】索引是排好序的数据结构，类似书的目录。MySQL InnoDB 默认用 B+ 树：非叶子节点只存 key 用于导航，叶子节点存整行（聚簇）或主键（非聚簇），且叶子间用双向链表串起来。查询时从根节点二分下钻，3 层 B+ 树就能存千万级数据，把全表扫描的 O(n) 降到 O(log n)。范围查询、有序遍历也快，因为叶子链表有序。

根(1→10→20)
 ├─ 1..9  → 叶子[1,3,5,7,9] ⇄ [10,12...]

【结合你的经验】交易流水表按 trans_no 建索引后，单笔校验从全表扫 30s 降到毫秒级，逐笔校验 1900+ 用例才跑得动。 【追问链】B+ 树和 B 树区别？→ 为什么不用哈希索引做范围查？ [ ] 已掌握

10. 聚簇索引 vs 非聚簇索引

【考点】数据与索引存储关系 + 回表。 【参考答案】聚簇索引（InnoDB 主键）叶子节点直接存整行数据，表数据即索引顺序；非聚簇索引（二级索引）叶子节点存主键值，查非索引列时需用主键回表再查一次。回表：二级索引命中后拿主键去聚簇索引取完整行，多次 IO。覆盖索引可避免回表。

-- id 主键(聚簇)，name 二级索引
SELECT * FROM user WHERE name='张三'; -- 先走 name 索引拿 id，再回表取整行

【结合你的经验】环境信息模块建表时我把高频查询字段放进联合索引做成覆盖索引，避免回表，列表接口从 200ms 降到 40ms。 【追问链】没显式主键 InnoDB 怎么办？→ 回表多少次算多？ [ ] 已掌握

11. 覆盖索引、联合索引、最左前缀原则

【考点】索引设计核心。 【参考答案】覆盖索引：查询列都在索引中，无需回表。联合索引：多列组合 (a,b,c)，按最左前缀原则生效——从最左列开始连续匹配才能用，如 WHERE a=1 AND b=2 能用，WHERE b=2 用不上。排序/分组也遵循最左前缀。设计上把区分度高、常过滤的列放前面。

-- 联合索引 (channel_id, status, trans_date)
SELECT * FROM trans WHERE channel_id=10 AND status='S'; -- 命中
SELECT * FROM trans WHERE status='S';                    -- 不命中（缺最左）

【结合你的经验】渠道+状态+日期是资金交易最高频查询组合，我建了 (channel_id, status, trans_date) 联合索引，回归查询整体提速明显。 【追问链】范围查询打断最左前缀怎么办？→ 索引列顺序怎么排最优？ [ ] 已掌握

12. 索引失效的 7 种场景

【考点】写出反例是加分项。 【参考答案】 1. 对索引列做函数运算：WHERE DATE(create_time)='2026-01-01' 2. 隐式类型转换：WHERE phone=13800000000（phone 是字符串） 3. 左模糊：WHERE name LIKE '%明'（右模糊可用） 4. 使用 OR 且部分列无索引：WHERE a=1 OR b=2（b 无索引则全扫） 5. 不等于/ NOT IN/ IS NOT NULL：WHERE status != 'S' 6. 违背最左前缀：WHERE b=2（联合索引 a,b 缺 a） 7. 索引列参与运算：WHERE amount+1>100

-- 反例：索引失效
SELECT * FROM trans WHERE DATE(trans_time)=CURDATE();  -- 函数
SELECT * FROM trans WHERE trans_no LIKE '%ABC';         -- 左模糊

【结合你的经验】曾定位一个慢查询就是 WHERE DATE(trans_time)=... 导致全表扫，改成 trans_time>=? AND trans_time<? 后走索引。 【追问链】OR 怎么改写能用索引？→ 不等于一定失效吗？ [ ] 已掌握

13. EXPLAIN 执行计划关键列

【考点】看懂慢 SQL。 【参考答案】 - type：访问类型，从好到差 const > eq_ref > ref > range > index > ALL，ALL 全表扫最差。 - key：实际使用的索引；NULL 表示没用索引。 - rows：预估扫描行数，越小越好。 - Extra：Using index 覆盖索引（好）；Using where 回表过滤；Using filesort 文件排序（差）；Using temporary 用临时表（差）。

EXPLAIN SELECT * FROM trans WHERE channel_id=10 AND status='S';

【结合你的经验】优化回归脚本时我先 EXPLAIN 看 type 是不是 ALL，发现是 ALL 就加联合索引，把 rows 从百万降到几百。 【追问链】ref 和 eq_ref 区别？→ possible_keys 有但 key 为 NULL 为什么？ [ ] 已掌握

14. 慢查询定位与优化完整步骤（5步法）

【考点】方法论。 【参考答案】① 开慢查询日志：slow_query_log=ON, long_query_time=1；② 用 EXPLAIN 看执行计划，找 type=ALL、rows 大、Extra 有 filesort/temporary；③ 定位原因：缺索引/索引失效/数据倾斜/锁等待；④ 改造：加索引、改 SQL（避免函数/左模糊）、拆大表、加 LIMIT；⑤ 验证：再 EXPLAIN + 压测对比耗时。

SET GLOBAL slow_query_log=ON;
SET GLOBAL long_query_time=1;

【结合你的经验】报文比对自动化上线后单轮 2 人天，我把慢 SQL 用上面 5 步法优化，建联合索引+改日期函数写法，最终降到 0.5 人天。 【追问链】慢日志文件太大怎么分析？→ 优化后还慢可能是锁？ [ ] 已掌握

15. 事务 ACID

【考点】基础必背。 【参考答案】 - A 原子性：事务内操作要么全成功要么全回滚（undo log 实现）。 - C 一致性：事务前后数据满足业务约束（如余额不为负）。 - I 隔离性：并发事务互不干扰（锁+MVCC 实现）。 - D 持久性：提交后数据永久保存（redo log + 刷盘实现）。 【结合你的经验】资金交易记账是典型事务场景，一笔扣款+"对方入账"必须原子，否则会出现钱丢失，我用事务保证一致性。 【追问链】MySQL 靠什么实现原子性和持久性？→ 一致性靠谁保证？ [ ] 已掌握

16. 事务隔离级别 4 种

【考点】脏读/不可重复读/幻读。 【参考答案】 - 读未提交：可能脏读（读到未提交数据）。 - 读已提交：解决脏读，可能有不可重复读。 - 可重复读：解决脏读+不可重复读，可能幻读（MySQL 默认，靠 MVCC 基本解决幻读）。 - 串行化：全解决，但性能差。

级别 脏读 不可重复读 幻读
读未提交 ✗ ✗ ✗
读已提交 ✓ ✗ ✗
可重复读 ✓ ✓ △
串行化 ✓ ✓ ✓
【结合你的经验】对账批量更新时若隔离级别太低，可能读到别人未提交的中间状态，导致对账差异，我们统一用可重复读。
【追问链】幻读和不可重复读区别？→ MySQL 怎么解决幻读？
[ ] 已掌握

17. MySQL 默认隔离级别与 MVCC

【考点】原理简述。 【参考答案】MySQL InnoDB 默认"可重复读（REPEATABLE READ）"。MVCC（多版本并发控制）靠 undo log 版本链 + 事务 ID + ReadView 实现：每行有隐藏的事务 ID 和回滚指针，读时根据 ReadView 找对自己可见的版本，读不加锁，读写不阻塞。快照读走 MVCC，当前读（SELECT...FOR UPDATE）走锁。 【结合你的经验】环境信息模块的 RBAC 权限查询并发高，靠 MVCC 快照读保证一致性的同时不影响写入性能。 【追问链】快照读和当前读分别是什么？→ undo log 什么时候清理？ [ ] 已掌握

18. 数据库锁：行锁/表锁/间隙锁

【考点】并发控制。 【参考答案】 - 行锁：锁单行，InnoDB 默认，并发高；靠索引命中才锁行，否则升级表锁。 - 表锁：锁整表，MyISAM 默认，并发低。 - 间隙锁：锁索引记录间的"间隙"，防止插入，解决幻读（RR 级别下）。 - 还有临键锁（Next-Key = 行锁+间隙锁）。 【结合你的经验】批量更新交易状态时，WHERE 走主键索引才锁行；曾因 WHERE 用非索引列导致锁升级，阻塞了其他渠道写入。 【追问链】怎么避免行锁升级表锁？→ 死锁和间隙锁关系？ [ ] 已掌握

19. MySQL vs Oracle 主要差异

20. 数据库三范式

【考点】通俗理解即可。 【参考答案】 - 1NF：字段原子不可再分（不加"地址"里塞省市区）。 - 2NF：非主键列完全依赖主键（消除部分依赖，针对联合主键）。 - 3NF：非主键列不传递依赖（如"部门名"依赖"部门ID"而非直接依赖"员工ID"）。 测试岗知道"范式为了减少冗余、避免更新异常"即可，实际为性能常反范式（冗余字段）建宽表。 【结合你的经验】资金报表为了查询快，会故意冗余渠道名称等字段做反范式宽表，我造数时要同步维护冗余列。 【追问链】反范式有什么代价？→ 什么时候该违反范式？ [ ] 已掌握

21. 主键 vs 唯一索引 vs 外键

【考点】约束区别。 【参考答案】 - 主键：唯一且非空，表只能一个，默认聚簇索引。 - 唯一索引：唯一可多列、允许一个 NULL，二级索引。 - 外键：保证引用完整性（子表值必须在父表存在），但互联网项目常不用外键靠应用层保证（性能/分库考量）。 【结合你的经验】环境信息模块 RBAC 用主键+唯一索引（如用户名唯一），外键我没在库里建，放在应用层校验，部署更灵活。 【追问链】主键和唯一索引底层都是 B+ 树吗？→ 为什么大表少用外键？ [ ] 已掌握

22. DROP/TRUNCATE/DELETE 区别

【考点】危险操作辨析。 【参考答案】 - DELETE：删行，可带 WHERE，走事务可回滚，逐行记日志，慢但安全。 - TRUNCATE：删全表，不可回滚（DDL），重置自增，快，不触发行级触发器。 - DROP：删表结构+数据，不可回滚。 测试造数后清理用 TRUNCATE 高效；生产严禁 TRUNCATE/DROP 误操作。

DELETE FROM tmp_trans WHERE day='2026-01-01'; -- 可回滚
TRUNCATE TABLE tmp_trans;                       -- 不可回滚

【结合你的经验】回归前我往临时表造数，跑完用 TRUNCATE 清临时表，比 DELETE 快且不留碎片。 【追问链】DELETE 没 WHERE 会怎样？→ 大表 DELETE 太慢怎么办？ [ ] 已掌握

25. 分页查询与深分页

【考点】性能陷阱。 【参考答案】MySQL 分页 LIMIT offset, size。深分页（offset 很大）慢：要先扫过 offset 行再取。优化：① 游标分页（where id>last_id limit n）；② 延迟关联（先查 id 再 JOIN 取详情）；③ 业务上禁止跳到极深页。

-- 深分页慢
SELECT * FROM trans ORDER BY id LIMIT 1000000, 20;
-- 优化：游标
SELECT * FROM trans WHERE id>1000000 ORDER BY id LIMIT 20;

【结合你的经验】环境信息模块列表接口早期用 LIMIT offset 深翻页卡死，改成"上一页最大 ID"游标后秒开。 【追问链】延迟关联怎么写？→ 游标分页缺点是什么？ [ ] 已掌握

26. COUNT(*)/COUNT(1)/COUNT(列)

【考点】计数语义。 【参考答案】 - COUNT()：统计行数，含 NULL，MySQL 做了优化最快。 - COUNT(1)：每行放常数 1 计数，含 NULL，性能≈COUNT()。 - COUNT(列)：统计该列非 NULL 的行，不含 NULL，最慢（需判空）。 结论：统计行数用 COUNT(*)；统计某列有值用 COUNT(列)。

SELECT COUNT(*) FROM trans;        -- 总行数
SELECT COUNT(status) FROM trans;  -- status 非空的行

【结合你的经验】回归统计"当日成功交易笔数"用 COUNT() 配 WHERE status='S'，确保口径和线上对账一致。 【追问链】MyISAM 和 InnoDB 的 COUNT() 差别？→ COUNT(DISTINCT 列)？ [ ] 已掌握

三、笔试实战（经典 SQL 笔试题 + 完整答案）

题1：连续登录天数（窗口函数经典） 表 user_login(uid, login_date)，求连续登录≥3天的用户。

SELECT uid, COUNT(*) AS continuous_days, MIN(login_date) start_dt, MAX(login_date) end_dt
FROM (
  SELECT uid, login_date,
    DATE_SUB(login_date, INTERVAL
      ROW_NUMBER() OVER(PARTITION BY uid ORDER BY login_date) DAY) AS grp
  FROM (SELECT DISTINCT uid, login_date FROM user_login) t1
) t2
GROUP BY uid, grp
HAVING COUNT(*) >= 3;

思路：用行号把连续日期"归零"成同一组，同组即连续。

题2：每个部门工资最高的前 2 名（TopN）

SELECT * FROM (
  SELECT dept_id, emp_name, salary,
    DENSE_RANK() OVER(PARTITION BY dept_id ORDER BY salary DESC) rk
  FROM emp
) t WHERE rk <= 2;

题3：删除重复记录只留一条

DELETE FROM trans
WHERE id NOT IN (
  SELECT min_id FROM (
    SELECT MIN(id) AS min_id FROM trans GROUP BY trans_no
  ) t
);

题4：分页取第 11-20 条（深分页优化）

-- 常规
SELECT * FROM trans ORDER BY id LIMIT 10, 10;
-- 游标优化（上页最大 id=100）
SELECT * FROM trans WHERE id > 100 ORDER BY id LIMIT 10;

题5：统计每个渠道成功/失败笔数与总金额（多聚合）

SELECT channel_id,
  COUNT(*) AS total,
  SUM(CASE WHEN status='S' THEN 1 ELSE 0 END) AS succ_cnt,
  SUM(CASE WHEN status='F' THEN 1 ELSE 0 END) AS fail_cnt,
  SUM(amount) AS total_amt
FROM trans
GROUP BY channel_id;

题6：找出"销售额比本部门平均高"的员工

SELECT e.* FROM emp e
JOIN (SELECT dept_id, AVG(salary) avg_sal FROM emp GROUP BY dept_id) d
  ON e.dept_id=d.dept_id
WHERE e.salary > d.avg_sal;

题7：账户余额环比（LAG）

SELECT acc_no, trans_date, balance,
  LAG(balance) OVER(PARTITION BY acc_no ORDER BY trans_date) prev,
  balance - LAG(balance) OVER(PARTITION BY acc_no ORDER BY trans_date) diff
FROM daily_balance;
